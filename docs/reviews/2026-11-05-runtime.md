# Runtime and architecture review

Reviewed 2026-11-05 UTC. Baseline: `main` at `2eaad4d`. The interrupted vector-weight
change was reviewed as a dirty diff and is now preserved at
`wip/vector-weight-storage-review` (`ca00777`). Production files were not edited.

This is a critical-path static review, not a proof that every line in the repository
is correct. Scope: the entire interrupted runtime diff; vector split/model producers
and consumers; storage access transitions; context/updater dispatch; shared Metal
memory lifetime; runtime initialization and synchronization; telemetry schema; and
build integration. Existing validation records were inspected. No heavy build or
test suite was run. One short read-only probe loaded the existing CPU library.

## Findings

### RT-1 — P1: the interrupted change can run a CPU transform over a CUDA view

**State:** confirmed unsafe source path in quarantined work, not in baseline main;
not executed on NVIDIA hardware.

At `ca00777`, `xgboost/src/tree/updater_quantile_hist.cc:280` changes root weights
from `weight.HostView()` to
`weight.View(ctx_->IsMPS() ? DeviceOrd::MPS() : ctx_->Device())`. Lines 287–289 then
run `std::transform` for every non-MPS context. With a CUDA context, this view points
to CUDA memory, which the CPU transform must not dereference.

This is reachable in source through explicit updater selection: `gbtree.cc:170`
passes the original context to the requested updater. `QuantileHistMaker` retains
that context; its gradient selection deliberately uses CPU for non-MPS at baseline
`updater_quantile_hist.cc:712`. `HistMultiEvaluator` also explicitly constructs its
tree evaluator on CPU (`evaluate_splits.h:1214`). Thus a shared CPU updater cannot
infer the memory for its host work from `ctx_->Device()`.

**Fix:** preserve `HostView()` for the non-MPS path. Select a Metal view only in the
Metal branch. No other root arithmetic needs changing.

**Acceptance:** CPU-only and Metal root/vector cases pass; a CUDA runtime check for
manual `grow_quantile_histmaker` with a CUDA context is added/run when an NVIDIA
runner is available. Compile-only CUDA CI cannot detect this invalid host access.
Do not merge the WIP change based only on its first successful local build.

### RT-2 — P2: CPU `metal_info()` omits 17 fields provided by Metal builds

**State:** confirmed baseline API defect, reproduced using the existing CPU dylib.

`xgboost/src/c_api/c_api.cc:275–294` emits AUC, group-sort, and ranking counters in
the Metal branch. Their zero-valued equivalents are absent from the non-Metal
branch. The CPU result has 261 keys; the baseline Metal source emits 278 keys.
Code such as `xgb.metal_info()["roc_auc_dispatches"]` therefore fails with a
`KeyError` on a CPU build instead of returning a zero diagnostic.

Missing fields:

```
group_sort_dispatches, group_sort_gpu_time_ns,
pr_auc_dispatches, pr_auc_gpu_time_ns,
ranking_bias_dispatches,
ranking_cache_dispatches, ranking_cache_gpu_time_ns,
ranking_gradient_dispatches, ranking_gradient_gpu_time_ns,
ranking_label_dispatches, ranking_label_gpu_time_ns,
ranking_metric_dispatches, ranking_metric_gpu_time_ns,
ranking_pair_batches, ranking_pairs,
roc_auc_dispatches, roc_auc_gpu_time_ns
```

`scripts/check_cpu_build.py` only verifies that fields which exist are zero. It
cannot discover missing fields. Probe evidence is in
`results/review-runtime-metal-info-schema.txt`.

**Fix now:** add the missing zero entries and a schema-key equality check. This is
a small isolated cleanup fix, not a reason to rewrite all telemetry.

**Acceptance:** Metal/non-Metal key sets match; all CPU counters are zero;
`built`/`available` retain their separate semantics. Existing 276 Statistics members
and 276 aggregate loads were checked and align (the first three have intentional
internal naming aliases), so no positional aggregate corruption was found.

### RT-3 — P1 relative to the stated full-port goal: vector payload placement is still incomplete

**State:** confirmed baseline coverage gap; the WIP change closes only part of it.

`tree/hist/evaluate_splits.h:619` keeps integer node and chosen-child sums in host
vectors. Lines 893–952 publish child sums, weights and category words to host
vectors, then copy selected payloads into host caches. Lines 1187–1193 copy integer
children into host node sums. Root weight gathering and multiplication are also
host work at `evaluate_splits.h:1092` and `updater_quantile_hist.cc:279`.

CUDA explicitly owns device `node_sums_`, `split_sums_`, `node_weights_` and
`split_cats_` in `tree/gpu_hist/multi_evaluate_splits.cuh:46–84`; the root launcher
uses a GPU weight view in `tree/updater_gpu_hist.cuh:295`. These are actual
producer/consumer placement differences, not a speculative inference from a
function name. Correct predicted values do not close them.

**Bound this as three tasks:** (1) root/child/model weights, (2) selected category
bitsets, (3) exact node/child gradient-state storage. Scalar control fields,
host node topology and upstream-defined serialization are not automatically GPU
porting tasks.

**Acceptance per task:** queued depthwise/lossguide candidates survive workspace
reuse and buffer growth; production consumers run before CPU inspection;
payload-readback/copy counters and ownership assertions prove the intended path;
fixed fixtures agree with the source-derived oracle and CPU where algorithms
agree. Keep scalar and vector contracts distinct. Do not mark all vector state
complete after merging the current weight work.

### RT-4 — P2: exact-capacity buffer growth creates quadratic copying

**State:** confirmed algorithmic performance issue; impact not benchmarked here.

`common/metal_histogram.mm:2292–2309`, `MetalVectorBuffer::Resize`, allocates exactly
`max(16, requested_bytes)` whenever the requested size exceeds capacity, then
blits the whole previous logical size. Repeated growth by one/few elements copies
`1 + 2 + ... + n` elements instead of amortized linear traffic. It also waits for
each copy. The new resident model/cache path would make this particularly visible
for incremental/lossguide tree growth.

**Fix in the performance phase:** geometric capacity growth or an explicit reserve
contract, with overflow/device-limit checks. Logical size and tail initialization
must remain separate from capacity.

**Acceptance:** growing a buffer in small increments preserves bit patterns,
performs O(log n) allocations and O(n) aggregate copy traffic, respects the device
limit, and retains existing shrink/reuse semantics. Measure tree-training impact;
do not promise a specific speedup from this static finding.

### RT-5 — P2: execution identity and storage defaults are conflated

**State:** documented architecture risk, not a newly demonstrated numerical bug.

`src/context.cc:112–116` resolves `device="mps"` to a CPU `DeviceOrd` for generic
storage. Consequently `Context::IsMPS()` and `Context::IsCPU()` are both true
(`include/xgboost/context.h:188–219`). Generic dispatch defaults to CPU unless an
individual caller explicitly selects Metal. This explains why the project keeps
finding storage/consumer gaps after kernels already exist.

**Fix the process first:** explicitly classify each remaining production caller
as Metal execution, source-defined CPU control, or a tracked gap. Do not blindly
replace every `HostSpan()` or change `Context::Device()` globally: many generic
consumers currently rely on these host semantics.

**Acceptance:** the finite CUDA caller inventory has a disposition for each entry,
with no unexplained MPS fallback in the required scope. A later context/storage
separation must preserve CPU/CUDA behavior and have integration tests, rather
than be mixed into each new operation.

### RT-6 — P2: the runtime is too concentrated and eagerly initializes every family

**State:** confirmed maintainability/startup coupling; startup cost not measured here.

Baseline has 10,628 lines in `metal_histogram.mm` and 8,292 in
`metal_histogram.metal`. The former implements memory, tensors, outputs,
collectives, sketches, objectives, metrics, SHAP, prediction and tree growth
despite its histogram name. It has 209 `make_pipeline(...)` calls plus directly
constructed pipelines; the shader contains 212 kernel entry points.
`Runtime()` compiles the entire shader and eagerly creates all those pipelines
(`metal_histogram.mm:349–590`) on the first runtime use. A failure in an unrelated
kernel can prevent a basic operation from starting.

**Bounded cleanup plan:** use the existing family headers as extraction boundaries.
First isolate runtime/memory/counter plumbing without arithmetic changes; then
extract at most one family per reviewed change. Keep shader source handling and
build dependencies explicit. Consider lazy pipeline creation separately after
measuring cold-start cost. Avoid a wholesale rewrite or mass reformat of 19k lines.

**Acceptance:** no public API or arithmetic changes in extraction commits; a
focused family suite plus integration smoke test passes; the full suite runs at
the extraction milestone. First-use and warm timings are reported separately.

### RT-7 — P2: synchronous completion limits the performance ceiling

**State:** confirmed design limitation, already disclosed; not a correctness failure.

`CompleteOperation` commits and waits on every operation
(`metal_histogram.mm:2254–2262`). Many call sites also do the same directly. The
WIP constraint path adds two separately completed snapshots before its update,
and the root path has separate finalize/store/copy/scale/model-copy commands.
These can be very small payloads. Moving arithmetic to a GPU does not alone make
this scheduling efficient.

**Plan:** after operation/storage coverage, profile command count/wait time and
batch adjacent operations under one submission where ownership permits. Preserve
explicit CPU/public API synchronization boundaries. Do not turn this review into
an asynchronous runtime rewrite now.

**Acceptance:** fixed benchmark cases report construction, cold start, warm train,
prediction, memory and command counts separately; correctness/lifetime/alias
checks pass with fewer intermediate waits. CPU wins are valid results.

## Positive evidence and limits

- The implementation has real custom Metal kernels and explicit producer/consumer
  paths; it is not merely a CPU implementation renamed MPS.
- Shared-memory borrowing performs alignment, VM-region, protection and size
  checks in `common/metal_memory.h`, with synchronous lifetime guidance. The WIP
  copy code explicitly retains alias snapshots around its autorelease pool. I did
  not identify a concrete lifetime defect in the sampled copy paths.
- GPU allocation access states, raw-bit copies, overflow checks, serialization
  boundaries and CPU-only stubs have substantial existing tests. They should be
  preserved instead of discarded during cleanup.
- I found no additional demonstrated baseline prediction-corruption bug in these
  sampled paths. This is not a clean bill of health for all 212 kernels. The
  independently discovered telemetry defect and quarantined unsafe CUDA branch
  show why passing aggregate test counts are insufficient review evidence.
- NVIDIA execution is absent. CUDA compiler success verifies compilation/linking,
  not host/device pointer safety or arithmetic/runtime equivalence.

## Recommended order and stopping rules

1. Keep unfinished feature work quarantined; preserve the known tested baseline.
2. Fix RT-2 with its schema regression; publish a short current-status README and
   one prioritized plan. Do not rerun the entire GPU suite for documentation.
3. Review/fix RT-1 before resuming the isolated vector-weight task. Then close
   each of the three RT-3 payload tasks with explicit acceptance evidence.
4. Finish a finite caller audit. Each candidate becomes implemented/tested,
   source-defined host work, unsupported-with-reason, or a concrete open task.
   An audit finding may add a task; it must not silently expand an existing task.
5. Resolve the known numerical-contract ledger once, with named tolerances and
   hardware limitations. Do not endlessly tighten CPU comparisons where CUDA
   intentionally uses a different algorithm/order.
6. Run one integration milestone across supported local configurations; retain
   separate CUDA compile/runtime status. Full parity stays unproven until the
   operation checklist and required hardware validation are addressed.
7. Optimize against a frozen benchmark matrix, starting with growth and command
   submission only if profiling supports their priority. Extract modules in
   arithmetic-preserving changes with a bounded scope.

No percentage-complete estimate is defensible from source-file coverage alone.
The next milestone can nevertheless be finite: the three named vector payload
tasks plus disposition of the already inventoried helper callers. Publish that
milestone's remaining task count rather than another chronological wall of logs.
