# Documentation review — 2026-11-04

Scope: repository entry point, status/claim clarity, getting-started instructions,
validation and benchmark discoverability. Source baseline: `2eaad4d`; this review
is not a runtime or CUDA-parity certification.

## Findings

1. **P2 — Current and historical validation results were mixed without a clear boundary.**
   At baseline `README.md:28` reported 3,554 Python passes, while its main
   Validation section at `README.md:1252` reported 1,278 passes under a
   “validated through 2026-11-04” label. Both are historical facts, but the
   document presented them as competing current status. The new README has
   one revision-qualified result and a direct evidence link. The old statement
   remains explicitly historical at
   `docs/archive/README-progress-2026-11-04.md:1260`.
   Acceptance: one current status location; every test total names the tested
   revision; previous totals remain only in dated evidence or the archive.

2. **P2 — The project entry point was a development transcript rather than a usable guide.**
   Baseline README contained 3,458 lines / 224,444 bytes. Build instructions began
   at line 897; feature, test, performance, checklist and chronological sections
   repeated the same operations with different maturity descriptions.
   The unfinished training-state checklist at baseline line 1661 did not explain
   what would finish it, while long preceding passages enumerated successful
   kernels. This obscured both progress and remaining work.
   Acceptance: concise README; separate current plan/review/parity documents;
   development history explicitly archived. Implemented in the owned files.

3. **P2 — Implementation, source alignment, runtime equivalence, and speed were too easy to conflate.**
   The former README did contain qualifications, but interleaved them with large
   pass counts and historical speed tables. Test counts and the 42-family /
   109-file inventory cannot establish complete CUDA parity; compile CI cannot
   establish CUDA runtime behavior. The new opening and validation section make
   those distinctions explicit, and no completion percentage is asserted.
   Acceptance: keep operation-level acceptance criteria in the plan; maintain
   source/file inventory as a structural check; qualify NVIDIA runtime evidence
   separately from Metal/CPU results.

4. **P2 — Historical performance numbers must not become claims about current HEAD.**
   `docs/PUBLISHED_BENCHMARKS.md` records useful workloads, machine details,
   strict-equivalence failures, and old implementation revisions. Later
   CUDA-alignment changes invalidate treating those numbers as measurements of
   the current code. The new README links the records and explicitly dates
   their applicability instead of duplicating headline speedups.
   Acceptance: future benchmark summary identifies commit, environment, raw
   measurements and correctness result; retain CPU wins and failed comparisons.

5. **P3 — Setup requirements were implicit or spread through the transcript.**
   The package metadata requires Python >=3.11, but the old build paragraph said
   only Python. Snappy is needed by the native test suite rather than production.
   PyTorch/MLX cover optional native tensor producers; federated gRPC has separate
   dependencies. The new build/test sections separate these requirements and
   include a complete runnable synthetic-data example.
   Acceptance: syntax-valid commands with local source PYTHONPATH and libomp
   configuration; clean-machine build/test reproducibility remains a separate
   validation task rather than a claimed result of this docs edit.
