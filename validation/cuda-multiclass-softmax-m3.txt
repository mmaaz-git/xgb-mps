CUDA-source multiclass gradients and prediction transforms
Date: 2026-11-04; Apple M3 MacBook Air, 8 CPU / 10 GPU cores, 16 GB.

Source authority
----------------
xgboost/src/objective/multiclass_obj.cu::GetGradient
xgboost/src/common/math.h::Softmax, FindMaxIndex

The gradient source evaluates one row per GPU thread, initializes its maximum
with positive FLT_MIN, uses fmaxf, and adds FP32 expf terms sequentially to a
double sum. It narrows the completed sum to FP32 before division. Hessian products
are left-associated FP32 and floored at 1e-16f AFTER weight multiplication.
Only the label class subtracts one from its probability before weighting.

The former Metal implementation repeated this scan for every class and used
compensated FP32 summation. Dedicated xgb_multiclass_objective now preserves the
source row mapping, arithmetic boundaries and double sum, reusing the existing
software FP32/binary64 helpers. Host Gradients selects this kernel with row count;
other objectives retain their existing kernel. One-label-per-row shape enforced.
Shared memory eligibility, overlap-safe staging and existing counters unchanged.

The dedicated xgb_multiclass_transform implements common::Softmax's different
initial maximum: its first margin. It stores exp terms, sums in binary64 and
reuses those terms for division. Argmax initializes from the first value and
uses strict ordered comparisons, retaining first ties, leading NaNs and
subnormal ordering. The old -FLT_MAX maximum loop skipped a leading NaN and
native comparisons could flush subnormals. Empty calls dispatch nothing.

Preserving positive FLT_MIN in gradient calculation is deliberate: uniformly
large negative margins can underflow ALL gradient exp terms, producing NaN
probabilities/gradients and floored Hessians. The same row's prediction transform
starts from its actual maximum and remains well-defined. This is source behavior,
not an attempt to repair CUDA numerics by substituting a different algorithm.

Numerical scope
---------------
The scalar test oracle uses explicit FP32 operations and host binary64 exp
rounded to FP32. Software GPU math produces those same sampled result bits;
NaNs compare by classification and signed zero by equality. Host common::Softmax
is also executed unmodified with its native expf, allowing four FP32 ULP; the
observed maximum is two. No NVIDIA GPU was used. Actual libdevice/NVCC contraction
and other Apple GPUs are unverified. No end-to-end performance benchmark was
run. Linear instead of quadratic row scanning does not establish measured speedup.
