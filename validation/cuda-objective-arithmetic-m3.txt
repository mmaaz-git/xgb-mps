CUDA-source generic objective and prediction-transform arithmetic
Date: 2026-11-04. Apple M3 Air, 8 CPU / 10 GPU cores, 16 GB.

Source authority and changes
----------------------------
Vendored objective/regression_loss.h, regression_obj.cu, hinge.cu,
quantile_obj.cu and common/math.h define the expressions.

xgb_objective and xgb_transform moved after the existing numerical helpers.
The previous xgb_multiclass_math namespace is now xgb_objective_math; shared
FMax, Sigmoid and SoftPlus implement the source comparison/branch rules.
Unused early native-float sigmoid/log1p/softplus helpers were removed.
No host API, dispatch, memory-sharing or statistics ABI change.

Generic objectives preserve FP32 boundaries, weight multiplication, scale_pos_weight
where passed by the production RegLossObj, and source branch semantics. Gamma
first transforms by FP32 exp. Pseudo-Huber retains its separate FP32 squares,
root and denominator. Poisson/Tweedie retain source terms and weight order.
Expectile retains cumulative FP32 margins, alpha selection (NaN >=0 is false),
FP32 sums, sigmoid gradient factor and squared sigmoid Hessian factor.

Squared-log: fmaxf clamp, FP32 log1p terms; FP32 numerator in source order;
binary64 pow(base,2) denominator and division; FP32 narrowing then fmaxf floor.
An FP32 base squared is exactly representable in binary64, so Metal uses the
software-double product. This differs from the former FP32 denominator in 25,205
weighted/unweighted corpus fields. Rewriting the numerator alone is algebraically
consistent under these rounding rules and produces ZERO corpus witnesses; this
part is source-order alignment, not an independent numerical bug fix.

Overload evidence: CUDA C++17 is configured in xgboost/cmake/Utils.cmake. NVIDIA
12.8.93 crt/math_functions.h around 5282 declares std::pow(_Tp,_Up) via
__gnu_cxx::__promote_2 for modern GCC/C++11+. GCC 14.2 ext/type_traits.h maps int to
double and combines it with float, yielding double. Modern libc++/MSVC overloads
also promote. The header's old float,int overload and NVRTC/global powif wrapper
are different conditional branches and are not the configured std::pow call.

GCC promotion traits:
https://github.com/gcc-mirror/gcc/blob/releases/gcc-14.2.0/libstdc%2B%2B-v3/include/ext/type_traits.h
Actual libdevice pow/compiler lowering on NVIDIA remains unverified.

Hinge label*2.0-1.0, p*y<1.0 and -y*w now use binary64, then narrow the gradient.
The other branch returns zero gradient and unweighted FLT_MIN Hessian. Native
checks distinguish the old FP32 version in 6,089 cases, including tiny fractional
labels near margin boundaries. Public label-validation behavior is unchanged.

Transforms preserve source FP32 sigmoid/exp/softplus and ordered comparisons.
Quantile keeps the source insertion sort, including NaN barriers, first equal
values, subnormal ordering and bit-preserving moves. Identity/empty calls do
not dispatch. No CPU correction path was added and no performance benchmark run.

Validation design and limits
----------------------------
tests/build_objective_reference.py extracts actual scalar loss methods and device
lambda bodies, rebinding views and substituting math callbacks only. Generated
source hashes are written to results/cuda_objective_reference_generated.h.
The reference rounds host binary64 exp/log1p/sqrt to FP32 and keeps pow binary64.
FP32 arithmetic is compiled with contraction off. Exact sampled result matches
are source-expression evidence, NOT libdevice/NVCC or cross-GPU bit equivalence.

CUDA fmaxf documents choosing the numeric operand when the other is NaN:
https://docs.nvidia.com/cuda/archive/13.0.1/cuda-math-api/cuda_math_api/group__CUDA__MATH__SINGLE.html
The first reference used Apple std::fmax, which propagates a signaling NaN:
  fmax(bits0x7fac34ed,-.999999f) -> NaN bits0x7fec34ed;
  fmax(bits0x7fec34ed,-.999999f) -> -.999999f bits0xbf7fffef.
That caused a test-reference failure (Metal clamped the NaN as documented for
CUDA). The CUDA reference now explicitly applies the documented missing-NaN
rule. A second reference retains native libm/fmax and records the differences.
No production change or numerical-tolerance increase was made for this failure.

  Per-kind differences / classification / beyond finite tolerance:
    square 0/0/0, logistic 633/0/5, squared log 35/12/8, gamma 1533/0/8,
    pseudo-Huber 0/0/0, Poisson 1631/0/10, Tweedie 2204/0/4, hinge 0/0/0,
    expectile 857/0/0.
  A host-only diagnostic replay (results/objective-native-diagnostic.log)
  isolates all 12 classification and 8 finite squared-log tolerance differences to
  signaling-NaN clamps. The other 27 finite tolerance differences are cancellation
  cases multiplied by weights 1e20/1e30. Example: Poisson margin=-.0744905472,
  label=.928216279, weight 1e30 gives oracle/Metal gradient=-5.96046457e22 while
  native-host expf yields exactly zero. This is a real cross-library distinction,
  not hidden by an enlarged test tolerance or a CPU correction.
  The maximum absolute error over all fields is not specifically the maximum
  among tolerance failures; large-scale finite values can have small relative
  error. Actual NVIDIA results for these cases remain unmeasured.
These are explicit stress-corpus differences, not a replacement CPU-equivalence
claim. The ordinary production-training comparisons keep their tolerances.
